# OpenSpec 评审摘要生成器

为 OpenSpec change 产物生成评审文档，按认知顺序（做什么 → 怎么做 → 哪里有风险）组织内容，帮助技术组长在开发评审会议上高效判断方案是否合理。

**定位区分（review vs design）**：
- design.md 天然详细，逐模块完整覆盖所有设计细节（含常规实现）+ 实现蓝图（面向 AI 代码生成）
- review.md 是 design 的**评审投影**——按人类阅读认知顺序重组，只提取值得在评审会议上讨论的核心技术要点，过滤掉常规/显而易见的实现和代码级蓝图
- 评审者看完 review.md 应能直接判断："这个方案可行 / 这里有问题需要讨论"

## 触发方式

用户调用时可指定 change 名称作为参数：
- `zwflow-review-doc-gen` Skill feat-export-csv — 为指定 change 生成评审文档
- `zwflow-review-doc-gen` Skill — 不指定时，列出所有 change 逐一处理

## 执行流程

### 1. 确定目标 change

**指定了 change 名称时：**
- 验证 `openspec/changes/<name>/` 目录存在
- 检查 design.md 和 specs/ 是否已生成（至少需要 specs，design 可选）
- 如果产物不完整，提示用户先完成产物再生成评审

**未指定 change 名称时：**
- 执行 `openspec list --changes --json` 获取所有 change
- 逐个检查是否已存在 `review.md`
- 已存在的，询问用户：覆盖 / 跳过
- 依次为需要处理的 change 生成评审文档

### 2. 读取产物并评估复杂度

按优先级读取以下文件：
1. `proposal.md` — 提取背景、变更目标、影响面（构建上下文）
2. `design.md` — 核心，提取全局决策 + 按模块提炼设计要点
3. `specs/` 目录下所有 spec.md — 理解行为规范、场景和 NFR
4. `tasks.md` — 了解实现规模和模块划分
5. `db.*.sql` / `db.*.js` — 如存在，提取 DDL 摘要

**简单 change 跳过判定**：读取产物后，如果满足以下全部条件，告知用户此 change 过于简单无需评审文档，确认后跳过：
- 无 design.md 或 design 中所有模块均为模式引用级（无架构说明段）
- 无全局决策表
- 无 Redis/队列/锁/异步任务设计
- 无 DDL 变更
- 总任务数 ≤ 3

### 3. 生成评审文档

### 4. Mermaid 图表规范（CRITICAL — 代码级标注）

所有图表 MUST 包含代码级标注，禁止纯业务文本描述：

| 图表元素 | MUST 标注 | 禁止写法 |
|----------|-----------|----------|
| 状态流转边 | `status=N`（字段值） + `(Service::method)` | "审核通过"、"状态变更" |
| 时序图消息 | `Service::method(key_param)` | "调用服务"、"处理请求" |
| 流程图条件 | 实际条件表达式 `amount >= 5000` | "金额较大时" |
| 流程图节点 | 含关键操作 `写入 Redis + 投递MQ` | "处理数据" |

**图表类型选择：**

| 设计内容特征 | 图表类型 | 标注要求 |
|-------------|----------|----------|
| 状态流转 | `stateDiagram-v2` | 每条边标注 status 字段值 + 触发方法 |
| 多服务调用链 | `sequenceDiagram` | 消息标注 `Class::method(params)` |
| 多步骤/条件分支 | `flowchart TD` | 条件框写实际表达式，操作框写具体动作 |
| 数据模型关系 | `erDiagram` | 标注关键字段和关联 |
| 模块依赖 | `flowchart TD` + subgraph | 标注调用方法和数据流向 |

允许多个图表（如一个时序图 + 一个状态图），但不超过 3 个。如果设计过于简单（仅字段增删），可省略图表节。

### 5. 设计要点筛选标准

**核心原则**：组长评审 = 判断方案是否可行。review 不需要解释「为什么选 A 不选 B」，只需要清晰呈现「方案 A 具体是什么」让组长判断。

**纯技术视角（CRITICAL）**：review 只呈现技术方案本身，不收录业务场景描述。spec 中的 GIVEN/WHEN/THEN 场景、分支条件、输入输出字段等业务规则不进入 review——评审者按需查看 spec 原文。

**MUST 收录（组长需要判断可行性的方案）：**
- 涉及性能权衡的方案（查询策略、批量方案、索引设计）
- 缓存方案的具体设计（key 结构、过期策略、一致性保证）
- 新引入的外部依赖
- 异步/队列方案的设计（消费模式、幂等保证）
- 并发安全策略（锁方案、竞态处理）
- 数据模型中有权衡的设计（字段冗余、反范式、分表）
- 降级和容错方案

**跳过（组长不需要看的）：**
- 标准 CRUD 接口的实现（没有选择空间的常规操作）
- 显而易见的字段新增/修改
- 框架标准用法（无争议的常规写法）
- 纯代码组织（目录、命名）
- 业务场景/分支条件（GIVEN/WHEN/THEN、筛选项、状态判断等）
- 常规输入校验规则（必填、格式、长度等）
- 决策理由/备选方案对比（组长只判断方案行不行，不审理由）

### 5.1 模块篇幅控制

**MUST 保留所有模块标题**——评审者需要看到覆盖全貌。但常规模块折叠为一行：

- **有技术决策的模块**：详写核心要点（方案是什么）
- **常规 CRUD 模块**（无技术选型、无性能考量、无风险点）：标题下仅写一行 `标准 CRUD 实现，无需评审讨论。`

判定标准：如果一个模块的 design 内容只包含标准文件结构表 + 模式引用级蓝图，无架构说明段、无 Redis/锁/队列设计 → 判定为常规模块。

### 6. 设计要点撰写原则

**具体性要求（CRITICAL — 禁止抽象概括）：**

每个要点 MUST 满足：读完这一条，组长能判断"这个方案可行/有问题"。呈现方案本身，不解释选择理由。

| 维度 | 必须呈现 | 禁止写法 |
|------|----------|----------|
| 缓存 | key 模式 + 数据类型 + TTL + 失效机制 | "使用 Redis 缓存" |
| 锁 | key + TTL + 锁内操作范围 | "加分布式锁" |
| 队列 | exchange/topic + producer + consumer + 幂等方式 | "异步处理" |
| 查询 | 具体 SQL 策略/索引利用方式 | "优化查询性能" |
| 状态机 | 字段名 + 各状态值(int) + 转换条件 | "状态流转" |
| 事务 | 事务边界（哪些操作在一个事务内） | "保证数据一致性" |

**格式要求：**
- 要点标题用加粗，一眼可定位
- 直接描述方案具体做法，不写「原因」「理由」「对比」
- 不照搬 design 原文，用评审视角精简重组

### 7. 变更概述撰写原则

**核心要求**：评审者看完变更概述后能回答"这个 change 在做什么、为什么做、影响什么"。

**具体规则：**
- **目标**：一句话，动宾结构，如"为 XX 模块新增 YY 能力"
- **背景**：不超过 2 句，仅保留理解动机必需的信息，删除冗余的历史描述
- **变更范围**：从 proposal 的 Capabilities 中提炼 2-5 个核心能力点，用一句话描述每个
- **影响面**：列出受影响的系统/模块/API/外部服务，不含实现细节

**禁止**：照搬 proposal 原文。review 的变更概述是 proposal 的精炼版，去掉所有"正确但无助于评审判断"的背景信息。

### 8. 全局决策表生成规则

**来源**：design.md 的 `## 全局决策（Global Decisions）` 表。

**筛选规则**：
- 组长需要判断可行性的决策 → MUST 收录
- 显而易见/唯一选择的决策 → 跳过
- design.md 无此节或全为显然决策 → 省略整个"全局决策"子节

**格式要求**：
- 只呈现"决策点"和"采用方案"两列，不写理由列
- 方案描述需具体到技术细节（类名/中间件/数据结构），禁止纯概念词

### 9. 数据库变更摘要生成规则

**生成条件**：change 目录下存在 `db.*.sql` / `db.*.js` 文件，或 design.md 包含"数据库变更"节。

**表格规则**：
- 操作列：`新建表` / `加字段` / `加索引` / `改字段类型` / `DROP TABLE` / `DROP COLUMN`
- 关键变更：概述核心字段/索引/约束的变化
- 注意事项：标注潜在风险
  - 破坏性操作标注 `⚠️ 破坏性`
  - 大表加字段标注 `⚠️ 锁表风险`（如表估算 > 100w 行）
  - 需要数据迁移标注 `⚠️ 需数据迁移`

**索引设计说明**（条件性，有新增索引时）：
- 每个索引说明服务的查询场景（哪个方法的什么查询模式）
- 联合索引说明列序理由

### 10. NFR 摘要生成规则

**生成条件**：specs/ 下任一 spec 的 NFR 部分有实质内容（非全部 N/A）。

**表格规则**：
- "方案支撑"列说明设计中哪些方案在支撑这个 NFR 目标，建立 NFR 与模块设计的关联
- 目标为 N/A 的维度行省略
- 全部 N/A → 整个节省略

### 11. 边界情况处理

- **简单 change**：满足跳过条件时（§2），告知用户无需生成评审文档，确认后跳过
- **无 design.md**：从 specs 中提炼隐含的技术方案，并在评审焦点中标注"本变更无独立设计文档，以下要点从 specs 推断"
- **多个 capability spec**：按 design.md 的模块划分组织（design 模块 > spec capability）
- **design 中有未解决问题（Open Issues）**：MUST 在评审焦点中高亮提示
- **有破坏性数据库操作**：在评审焦点表中明确标注 DROP/TRUNCATE 等操作及影响范围
- **所有模块均为常规实现**：触发简单 change 跳过判定（§2）
- **design 无 Redis/队列/异步任务**：资源清单节整体省略
- **无 proposal.md**：变更概述从 design 概述节和 specs 推断，标注"无独立 proposal"
- **整个 change 无风险点**：风险与评审焦点节省略

### 12. 资源清单生成规则

资源清单是 design.md 中所有模块涉及资源的**全量汇总**，便于评审者一览全局和后续运维查阅。

**生成条件**：
- design.md 中任一模块涉及 Redis 操作 → 生成 Redis Key 表
- design.md 中任一模块涉及消息队列 → 生成消息队列表
- design.md 中任一模块涉及异步/定时任务 → 生成异步任务表
- 三者均不涉及 → 整个"资源清单"节省略

**Redis Key 表规则**：
- 动态参数用 `{参数名}` 占位符
- TTL 写具体数值+单位；无过期写 `无 TTL`；随机偏移写 `600s ± 30s`
- 失效触发：精确到方法级，格式 `XxxService::method() → del`；仅靠过期写 `自动过期`；跨模块失效同样列出
- 包含所有类型：缓存 + 锁 + 计数器/限流

**消息队列表规则**：
- Producer 和 Consumer 必须写出具体类名::方法名
- 消费模式：写明并发度（如"4 worker × 2 协程"）或顺序消费
- 幂等策略：写明具体去重方式（唯一键/幂等表/状态机判定）

**异步任务表规则**：
- 区分 Cron 定时 / Event 事件触发 / Manual 手动触发
- 频率具体到 cron 表达式或事件名
- 失败处理写明重试次数和最终处理方式

## 完成后

告知用户评审文档已生成及其路径。如果是批量生成，给出生成汇总（成功 N 个，跳过 N 个）。
随后根据变更复杂度提示：
- 正式功能开发（含业务逻辑）：执行 `zwflow-run` Skill <change-name> 启动融合执行。
- 简单/声明式变更（配置、DDL、DTO）：执行 `openspec-apply-change` Skill <change-name> 轻量实现。
