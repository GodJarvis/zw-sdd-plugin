# 上线文档生成器

从多个已完成的 OpenSpec change 中提取上线所需的操作项，聚合生成结构化的上线文档，供团队按步骤执行。

**参考标准示例**：生成前 MUST 阅读 `references/example.md`，严格对标其格式输出。

## 执行流程

### 1. 收集版本号

如果用户通过调用参数传入了版本号（如 `v1.7`），直接使用。

否则询问版本号（如 `v1.7`）。

### 2. 选择 change

列出 `openspec/changes/` 下所有 change 目录，以多选形式让用户勾选本次上线包含的 change。

显示格式：每个 change 附带 proposal.md 中的一句话描述（如有），帮助用户识别。

### 3. 提取上线内容

先识别当前项目框架，并读取 `references/frameworks/<framework>.md`。框架引用负责补充基础设施类型、任务运行方式、扫描关键字和命令命名规则；以下流程只定义两个框架共享的聚合行为。

对每个选中的 change，扫描产物提取以下信息：

#### DDL 变更
- 读取 change 目录下所有 `db.*.sql` 文件
- 按数据库类型分组（MySQL、MongoDB、StarRocks）

#### 基础设施变更
- 从 `design.md`、`tasks.md` 中提取需要额外操作的基础设施配置：
  - 创建消息队列、流或其他异步基础设施
  - 创建外部数据表（如 Hologres、ClickHouse）
  - 配置新的中间件或第三方服务
  - 其他需要在代码部署前/后手动操作的基础设施

#### 任务配置
- 从 `tasks.md` 和 `design.md` 中提取：
  - **常驻任务**：需要启动/重启/新增的消息队列消费者、守护进程
  - **定时任务**：需要新增/修改的 cron 任务
  - **一次性脚本**：需要执行一次的数据迁移/修复脚本
- 使用框架引用中定义的关键字、命令格式和命名约束扫描任务信息。

#### 代码合并信息
- 从 change 关联的分支名推断项目和分支
- 项目名从当前工作目录推断
- 合并方向固定为：`版本分支 → release → master`

### 4. 预览确认

将完整的上线文档内容直接输出到对话中，供用户预览。用户确认无误后再写入文件；如有修改意见则根据反馈调整后重新输出，直到用户确认。

### 5. 写入文件

用户确认后，将文档内容写入：`openspec/deploys/{版本号}-上线文档.md`

### 6. 文档结构（MUST 严格遵循）

```markdown
# {项目名}{版本号}上线文档

上线时间：{日期，格式 YYYY-MM-DD}

* [ ] 上线文档审核：@姓名

版本内容：

* {change 1 的一句话功能标题}
* {change 2 的一句话功能标题}
* ...

{按部署依赖顺序编排的步骤列表}
```

### 7. 步骤编排规则

步骤由产物内容驱动，按**部署依赖顺序**自动编排。典型顺序：

1. 数据库 DDL（代码依赖新表/新列）
2. 基础设施准备（创建 topic、外部表等）
3. 后端代码合并
4. 前端代码合并（如有）
5. 新建/配置任务（常驻消费者、定时任务）
6. 启动任务
7. 执行一次性脚本（数据迁移等）

**规则**：
- 仅生成有实际内容的步骤，无内容的类别跳过
- 步骤编号连续（第一步、第二步...）
- 每个步骤描述 MUST 具体（如"线上MySQL数据库执行SQL"而非"执行SQL"）
- 如果某个步骤涉及外部团队配合（如大数据团队），在步骤描述中体现

### 8. 格式规范（MUST）

#### 步骤 checkbox
```
* [ ] 第N步：{具体操作描述} @姓名
```

#### 人员标注
- 统一使用 `@姓名` 占位
- 不同步骤可以有不同/多个负责人占位
- **禁止在生成时询问用户人员信息**

#### SQL 代码块
- 使用 ` ```text/x-sql ` 语法标记
- 直接输出 SQL 内容，**禁止**附带"来源"、"说明"、"部署顺序"等任何注释
- 多条 SQL 可以分多个代码块

#### 合并代码步骤
```
* [ ] 第N步：{项目名}项目合并代码：

    * [ ] {版本分支}->release: @姓名
        {待填写 MR 链接}

    * [ ] release->master: @姓名
        {待填写 MR 链接}
```

#### 任务配置步骤
```
* [ ] 第N步：{项目名}线上服务器新建{任务类型} @姓名

    | 任务名称 | 任务描述 | 任务命令 | 定时时间 | 相关队列 |
    | --- | --- | --- | --- | --- |
    | {Name} | {描述} | {命令} | 常驻/cron表达式 | {队列信息} |
```

#### 版本内容
- 每条用 `*` 开头
- 仅一句话功能标题，从 proposal.md 提取
- **禁止**编号、嵌套列表、实现细节描述

### 9. 严格禁止（NEVER）

- ❌ 生成"上线后确认事项"或任何额外 section
- ❌ 在步骤间添加 `---` 分隔线
- ❌ 使用 `###` 等子标题
- ❌ 在 SQL 代码块前后添加注释说明（来源、说明、部署顺序）
- ❌ 版本内容中包含实现细节、字段名、接口名等技术描述
- ❌ 询问用户负责人/审核人/上线时间
- ❌ 在文档末尾添加不在模板结构中的内容

### 10. 缺失信息处理

- DDL 文件不存在 → 跳过 SQL 步骤
- 无法识别任务配置 → 跳过任务步骤
- 一次性脚本信息不完整 → 生成框架行，命令处写 `待补充`
- MR 链接 → 用 `{待填写 MR 链接}` 占位
- 上线时间 → 留空或写入用户指定的日期

## 完成后

告知用户文档已生成路径，提醒：
1. 填写各步骤负责人姓名（替换 `@姓名` 占位）
2. 填写 MR 链接
3. 确认上线时间
4. 按上线文档包含的 change 逐个执行 `openspec-archive-change` Skill <change-name> 归档，全部归档后执行 `zwflow-finish` Skill <change-name> 分支收尾
