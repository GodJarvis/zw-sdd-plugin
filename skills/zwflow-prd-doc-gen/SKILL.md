从用户的需求描述、原型截图或口头说明生成纯产品需求文档（PRD）。

PRD 是 propose 阶段的前置输入，确保需求与技术设计完全分离。PRD 只回答"做什么"和"为什么做"，绝不涉及"怎么做"。

---

**输入**：change 名称（可选）。可附带需求描述文本、截图路径、原型链接。

**步骤**

1. **确认元信息并确定 change**

   **先确认版本**：
   - 已有 `prd.md` 或 `proposal.md` 时，优先读取其中的 `version`；两个文件都存在时其值必须一致
   - 无可继承版本时，询问："本次需求关联的标准版本号是？（使用 v主版本.次版本.修订版本，如 v2.1.0；非版本开发填'项目维护'）"
   - 标准版本只接受 `^v[0-9]+\.[0-9]+\.[0-9]+$` 或 `项目维护`；禁止使用缺少修订号的版本、占位值或自行猜测
   - 将标准版本转换为目录版本标识：`v2.1.0` → `v2-1-0`，`项目维护` → `maintenance`

   **再确定名称**：
   - 新建 change 的格式固定为 `<类型>-<版本标识>-<主题>`，类型仅允许 `feat`、`fix`、`hotfix`
   - 完整名称必须匹配 `^(feat|fix|hotfix)-(v[0-9]+-[0-9]+-[0-9]+|maintenance)-[a-z0-9]+(?:-[a-z0-9]+)*$`
   - 如果未提供名称，逐项确认变更类型和主题，根据已确认版本自动生成名称；不得要求用户手工转换版本标识
   - 如果提供的名称对应新建目录，校验其版本标识与标准版本完全一致；缺少版本标识或不一致时，先展示规范化名称并等待用户确认，不得创建原名称
   - 如果名称对应已存在目录，读取并核对 `prd.md`、`proposal.md` 的 frontmatter。符合新格式时目录版本标识必须与 frontmatter 一致；不一致时停止并请求修正
   - 升级前已存在且不含版本标识的目录可继续补充，不自动重命名；仍须保证已有 frontmatter 版本一致

   **创建或进入**：
   - 目录存在且 `prd.md` 已存在 → 进入**补充模式**（见步骤 2a）
   - 目录存在但无 `prd.md` → 直接使用，进入新建模式（步骤 2）
   - 目录不存在 → 确认不与现有 change 同名后执行 `openspec new change "<name>"`，进入新建模式

   **操作人**：询问操作人姓名（如已知可跳过）。

2. **收集需求信息（新建模式）**

   询问：
   > "请描述你的需求。可以是：
   > - 文字描述（功能、背景、目标）
   > - 截图路径（原型图、设计稿）
   > - 以上的组合
   >
   > 尽量说清楚：为什么要做、做成什么样、验收标准是什么。"

   如果用户提供了截图路径，使用当前宿主可用的文件或图片读取能力理解内容。

   **关键**：如果用户的输入中包含技术实现细节（表名、API、架构方案），提取需求本质，丢弃技术描述。生成后提示用户："你提到的技术思路会在 propose 阶段的 design.md 中体现。"

2a. **补充需求说明（补充模式）**

   当 change 已存在且 prd.md 已有内容时：
   1. 读取现有 prd.md 内容，展示当前功能点摘要
   2. 询问："当前 PRD 已有以下功能点：\n<列表>\n\n请描述需要补充的业务需求。"
   3. 收集用户补充内容
   4. 将新需求**追加合并**到现有 PRD 中（新增功能点、补充验收标准等），不覆盖已有内容
   5. 跳转到步骤 5（确认并引导下一步）

3. **探索代码库**

   根据需求描述，快速探索项目中相关模块：
   - 确定影响范围（涉及哪些业务模块）
   - 理解当前功能边界（Non-Goals 的依据）

4. **生成 PRD**

   按以下模板生成，写入 `openspec/changes/<name>/prd.md`：

   ```markdown
   ---
   version: <标准版本号，如 v2.1.0；目录为 v2-1-0。非版本开发填"项目维护"，目录为 maintenance>
   author: <操作人姓名>
   created: YYYY-MM-DD
   updated: YYYY-MM-DD
   ---

   # <功能名称> 产品需求文档

   ## 背景（为什么做）

   <!-- 业务背景、问题现状、解决什么痛点 -->

   ## 目标（做成什么样）

   <!-- 可衡量的预期结果。对用户/业务的价值。 -->

   ## 功能描述（做什么）

   ### 功能点 1：<名称>
   <!-- 详细描述功能行为、用户流程、业务规则 -->

   ### 功能点 2：<名称>
   <!-- ... -->

   ## 验收标准（怎么算做完）

   - [ ] <具体可测试的条件>
   - [ ] ...

   ## Non-Goals（不做什么）

   - <明确排除的范围>

   ## 影响范围（涉及哪些模块）

   - <受影响的业务模块名称>
   ```

5. **确认并引导下一步**

   展示 PRD 摘要后，检查 change 目录下产物状态：

   **情况 A：已存在 OpenSpec 产物**（proposal.md / specs / design.md / tasks.md 中任一存在）
   - 询问："检测到该 change 已有产物文档。PRD 内容变更可能影响现有产物，是否需要基于更新后的 PRD 重新生成受影响的产物？"
   - 用户确认 → 提示执行 `openspec-propose` Skill <name> 重新生成（propose 会读取最新 prd.md）
   - 用户拒绝 → 仅保存 PRD，不做后续操作

   **情况 B：尚无 OpenSpec 产物**
   - 提示："PRD 已生成：`openspec/changes/<name>/prd.md`"
   - "请审阅内容，确认无误后执行 `openspec-propose` Skill <name> 生成技术方案"
   - "propose 阶段会自动读取 prd.md 作为需求输入"

**写作原则**

- **零技术细节**：不提及数据库表名、字段名、API 路径、类名、框架概念
- **业务语言**：用业务术语（"用户可以导出订单" 而非 "新增 /api/export 接口"）
- **可测试**：验收标准必须是可通过黑盒测试验证的
- **完整**：每个功能点的边界情况、异常情况在功能描述中说清楚
- **精炼**：每句话都传递信息，不写废话

**禁止内容（从用户输入中提取需求本质后丢弃）**

- 数据库 Schema 设计 / SQL 语句
- API 路由定义 / 接口路径
- 代码架构方案 / 类图 / 时序图
- 具体技术选型（Redis / MQ / 等）
- 框架特定概念（Controller / Service / Model）

**护栏**

- PRD 中出现任何技术实现词汇 → 必须改写为业务描述
- 需求不清晰 → 追问用户，不自行脑补
- 用户说"用 Redis 做缓存" → PRD 中写"系统需支持高频访问下的快速响应"
- prd.md 不是 openspec 正式 artifact，是 propose 的输入材料
- 补充模式下只追加/修改内容，不删除已有功能点（除非用户明确要求）
- 生成完成后不要自动执行 propose，等待用户审阅确认
