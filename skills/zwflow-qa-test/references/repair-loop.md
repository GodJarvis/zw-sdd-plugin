# 并行多轨修复循环

> 本文档定义 Phase 4（多轨修复循环）的完整规则。
>
> **目标**：所有 TC 全部通过。不存在 SKIP 终态。

---

## 并行三轨道模型

Phase 4 启动时，三条轨道**同时激活**：

```
┌─ 轨道 A：数据补充 ────→ 列出清单 → 暂停等用户 → 收到数据 → 重跑
├─ 轨道 B：产物修复 ────→ AI分析不一致 → 确认方向 → 修复 → 重跑
└─ 轨道 C：代码修复 ────→ AI分析bug → 修复 → 护栏 → 重跑
                                    ↓
                            汇合点：全量回归
```

**关键约束**：
- 轨道 A 暂停等待用户期间，B 和 C 不阻塞
- 各轨道独立推进，不互相等待
- 同一轨道内如涉及多个 TC 的修复，可并行处理（如多个代码修复用独立 Agent）

---

## 轨道 A：数据补充

> **适用范围**：仅处理 Phase 2 中优先级 P4 标记的数据（无法自造的外部数据）。P1-P3 的数据问题不应出现在此轨道。

1. 列出所有需要真实数据的 TC 及其所需数据：

   ```
   以下用例需要真实外部数据（无法在测试中自动构造）：

   | TC | 所需数据 | 说明 |
   |----|---------|------|
   | TC-002 | 有效的 zm_id | 第三方平台掌微号，需要 staging 中真实存在 |
   | TC-004 | 有效的 userid | 企微平台真实客服 userid |
   ```

2. 暂停，等待用户提供数据
3. 用户补充后替换测试代码中的 `PLACEHOLDER_NEED_REAL_DATA` 占位常量
4. 重跑相关 TC，更新状态

---

## 轨道 B：产物修复 + 用例质量缺陷处理

> **适用范围**：接口文档与实际实现不一致（原职责）+ 用例文档自身质量问题（占位符/语义歧义/断言方向存疑）。即使用例最终通过，发现的质量缺陷也 MUST 反馈回 qa-doc.md 修正（通过 ≠ 用例文档无误）。

1. 列出不一致项及质量缺陷：

   ```
   以下用例因接口文档与实际实现不一致而失败：

   | TC | 不一致点 | 建议修复 |
   |----|---------|---------|
   | TC-001 | 文档未标注 userid 必填 | 更新 yapi.md + qa-doc.md 补充该字段 |
   | TC-013 | 文档字段名 id，实际为 _id | 更新 yapi.md 字段名 |

   以下用例存在文档质量缺陷（即使通过也需修正 qa-doc.md）：

   | TC | 缺陷类型 | 建议修复 |
   |----|---------|---------|
   | TC-303 | WHEN/THEN 含裸占位符 `[具体任务ID]` | 改为「运行时动态获取」或填真实示例值 |
   | TC-0XX | THEN 语义歧义（主表述与括号方向相反） | 暂停问用户确认正确语义后修正 |
   ```

2. **质量缺陷分级处理**：
   - **影响断言方向**（如主表述与括号方向相反可能导致测试反向通过）→ 暂停询问用户，确认正确语义后修正 qa-doc.md 再重跑
   - **不影响断言方向的表述瑕疵/占位符** → 记录到报告 + 直接修正 qa-doc.md（填真实示例值或改为「运行时动态获取」说明）后继续，不必每次暂停
3. 引导用户确认修复方向（修文档 or 修实现）
4. 根据用户决策修复对应产物（yapi.md / qa-doc.md）或调整测试代码
5. 重跑相关 TC，更新状态

---

## 轨道 C：代码修复

1. AI 分析失败原因并修复业务代码
2. 每次修复后：
   - 编码护栏强制校验（对照当前宿主根指令文件的编码护栏逐条验证）
   - 重跑失败的测试确认修复生效
3. 同一测试连续 3 次 FAIL → 触发 `zwflow-debug` Skill 系统化调试
4. 重跑相关 TC，更新状态

---

## 汇合点：全量回归

三条轨道全部完成后：

1. 全量重跑所有 TC
2. 如有新增失败 → 重新分类 → 继续循环
3. 所有 TC 全部 PASS → 退出循环，进入 Phase 5

---

## 修复约束

- **修复范围不限**：按实际问题按需，可能涉及 Service/Model/Config/常量/产物文档等
- **编码护栏**：每个修改的代码文件 MUST 立即执行编码护栏校验
- **Commit 格式**：`fix(qa-test): 修复 TC-NNN 发现的问题 — {简述}`
- **Commit 时机**：每修复一组相关问题后 commit（不必每个 TC 单独 commit，相关联的可合并）
- **核心配置隔离规则**（遵守当前项目根指令中的配置变更护栏）：
  - 修改框架引用列出的受保护配置时 MUST 暂停修复循环，禁止继续直接编辑
  - 提示用户该路径属于核心配置范围，需要创建 `fix-*` 或 `hotfix-*` change；如项目根指令允许特定配置豁免，仍须获得用户明确确认
  - 禁止用 `fix(qa-test): 修复 TC-NNN` commit 格式包裹受保护配置修改
  - 报告中将此类修改单列为「需 openspec 流程确认的配置变更」，与业务代码修复分列，并附用户裁定结论

## 产物理清约束

- **修复代码的 commit 与 change 级 TDD commit 分开**（格式不同）
- **产物修复（yapi.md / qa-doc.md）需用户确认方向后再执行**

---

## 用例无效处理

如果修复过程中发现某个 TC 用例本身有误（如文档需求已变更、用例设计不合理），需用户确认后：

1. 从测试文件中删除该测试方法
2. 同步更新 qa-doc.md 中对应条目（标注删除原因）
3. 该 TC 在最终报告中标记为 `🗑️ REMOVED`，附删除原因

> 不允许「静默跳过」——要么修复通过，要么经用户确认后移除。
