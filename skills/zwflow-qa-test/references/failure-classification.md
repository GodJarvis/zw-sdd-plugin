# 失败分类规则

> 本文档定义 Phase 3（运行测试 & 失败分类）的完整规则。
> 执行本文件前必须已经加载 `references/frameworks/<framework>.md`。

---

## 环境预检（运行测试前 MUST 执行）

> 对应 SKILL.md Phase 2.5。运行测试前 MUST 完成以下轻量预检（只检查、不修改框架引用定义的核心配置，遵守当前项目根指令中的配置变更护栏）。任一项失败则暂停，列出问题清单等用户确认补齐方式后再运行测试。

| # | 预检项 | 检查方式 | 失败处理 |
|---|--------|---------|---------|
| 1 | 当前环境文件存在性 | 按框架引用检查环境文件 | 缺失则 MUST 暂停并询问用户，禁止静默创建或从其他环境复制；用户明确指定复制源时先展示 HOST/DB/REDIS 等关键差异 |
| 2 | 关键 HOST 配置非默认回落值 | 按框架引用读取配置源，确认认证/数据依赖的外部服务 HOST 非 `127.0.0.1` | 回落默认值则提示用户配置正确 HOST 后继续 |
| 3 | 外部服务连通性 | 容器内 `curl` 认证/数据依赖的外部服务（如 zhangquan）健康端点 | 不可达则暂停，提示用户排查网络/配置（**禁止直接进入 mock 方案，见 § 外部依赖故障决策树**） |
| 4 | DB 连通性 | 涉及 DB（PG/MySQL/Hologres）的 TCP+握手测试（`nc -zv host port` 或 PG `\conninfo`） | 握手超时则暂停，提示用户排查 DB 连通性 |
| 5 | 冒烟测试 | 运行任一已存在 HTTP 集成测试（如 ExampleIntegrationTest）验证测试框架+中间件链端到端可用 | 冒烟失败则暂停——能立即暴露“所有 HTTP 测试均挂起”的链路级故障（如中间件配置错误），**禁止跳过此步直接跑 QA 用例** |

> 预检是“检查”而非“修改”核心配置。预检失败按性质分流：外部服务不可达/DB 超时类（预检项 3/4）按 § 外部依赖故障决策树处理；配置文件缺失/HOST 回落/冒烟失败类（预检项 1/2/5）直接暂停并询问用户，不走决策树。任何预检失败都不得在预检阶段修改框架引用列出的受保护配置。

## 外部依赖故障决策树（遇外部依赖超时 MUST 遵守）

> 遇认证/DB/外部服务超时时，禁止跳过下列步骤直接进入 mock/绕过方案。MUST 按顺序完成前 3 步，仅当前 3 步均不可行且经用户明确同意后才进入步骤 4（mock 兜底）。

```
外部依赖超时
  ↓
步骤 1：连通性探测 — curl/TCP 对失败涉及的外部依赖
  ├── 可达 → 步骤 2
  └── 不可达 → 暂停，提示用户排查网络/防火墙/服务状态
步骤 2：配置核验 — 框架引用指定的环境文件存在、HOST 非默认回落值且关键变量已加载
  ├── 配置正确 → 步骤 3
  └── 配置缺失/回落默认值 → 暂停，提示用户补齐配置（禁止静默创建环境配置）
步骤 3：真实凭据路径 — 询问用户是否可提供真实凭据（如 Auth-Id）走真实链路
  ├── 可提供 → 使用真实链路（如 postWithAuth 设置 Auth-Id header 走真实 zhangquan 认证）
  └── 不可提供 → 步骤 4
步骤 4：mock 兜底（最后手段）— MUST 向用户说明理由，经用户明确同意后才实施
```

**Guardrail**：遇外部依赖超时，禁止直接进入 mock/绕过方案，必须先完成 host 配置 + 连通性 + 冒烟排查；确认环境无误后仍超时，方可考虑 mock 并需向用户说明理由。认证默认走真实 Auth-Id header 链路（见 test-code-generation.md § 代码生成 鉴权配置），非 mock。

## 运行 QA 测试套件

执行框架引用中的“QA 测试命令”。

**如果全部通过（0 失败）**：直接进入 Phase 5，执行 Level 1 简化 Review。

### 分批运行（连接池/资源超时时）

全量并发运行若出现**非断言失败**的间歇性超时（如连接池耗尽、跳板机 `max_connections` 限制），且 Flaky 重试 1 次仍超时，则切换分批运行：

使用框架引用中的“分批测试命令”，按 `--list-tests` 结果每批运行 3-4 个用例。

- 分批优先按测试文件或 `--list-tests` 分组（`--filter` 需方法名，注意转义）
- 此类超时**不进入 Phase 4 代码修复轨道**（非断言失败，属环境性资源超时）
- 实际采用的运行方式（全量/分批及每批用例）MUST 记录到报告「执行策略」节

### Flaky 自动重试

运行测试后，对所有失败 TC 自动重试 1 次（避免网络抖动/连接池耗尽等偶发因素触发不必要的修复循环）：

```
运行测试 → 有失败
  ↓
对每个失败 TC 重试 1 次
  ├── 重试通过 → 标记为 ⚡ FLAKY，从失败列表移除
  └── 重试仍失败 → 正常进入根因分类
```

- Flaky TC 在最终报告中标记为 `⚡ FLAKY`，不计入失败
- 报告概览中新增 `⚡ Flaky（重试通过）` 行
- Flaky TC 数量 ≥ 总数 10% 时 → 额外提示"测试环境可能不稳定"

### 空通过识别（THEN 专属断言 = 0）

通过的 TC 中，若**THEN 专属断言数为 0** 即标记为 ⚠️ **空洞通过**，不计正常 PASS：

- **THEN 专属断言数 = 该 TC 在 qa-doc.md THEN 节点明确声明的业务内容断言数量**（以用例文档为源头正向统计，非扫描测试代码方法名）。测试代码中对应这些声明的断言方计入；结构/分页/字段存在性等契约断言天然不属 THEN 业务声明，无需枚举排除
- 典型成因：测试代码 `if (!empty($records))` 才校验，staging 无数据时 0 断言直接通过
- 空洞通过的 TC MUST 暂停询问用户：无数据是否可接受（注明 vacuous 通过）/ 改为 `markTestSkipped` / 调整测试使有数据
- **触发条件**：THEN 专属断言数 = 0（非方法总断言数 = 0，后者因结构断言前置而永不命中）
- 报告用例明细表对空洞通过标注 ⚠️，与正常 PASS 区分

## 失败根因分类

对所有失败 TC 进行根因分析，归纳为**动态中文分类标签**。不使用固定 ABCD 编码——每次根据实际失败情况自行归纳分类名。

### 常见分类参考

以下为参考示例，实际以当次结果为准：

| 分类名 | 根因说明 |
|--------|---------|
| 接口文档与实际实现不一致 | 如必填字段文档未标注、字段名差异、响应结构与 yapi.md 不匹配 |
| 服务端缺少参数校验 | 如类型/边界/枚举未校验、空值/null 被接受 |
| 测试环境数据缺失 | 如 staging 无对应测试账号/记录、外部平台数据不存在 |
| 服务端业务逻辑 bug | 如接口行为与预期不符、状态转换逻辑错误 |
| 测试代码生成偏差 | 如 AI 对 GIVEN/WHEN/THEN 理解有误、断言不准确 |
| 测试基础设施故障 | 如环境配置缺失、HOST 回落默认值、中间件配置错误、外部服务不可达——**MUST 先排查本地配置+连通性，确认非本地可修复才可标记“需 staging”**，禁止将未排查的配置问题直接归为环境不可达 |

> **分类边界**：「测试基础设施故障」= 测试无法执行到业务层（配置/连通性/中间件问题）；「测试环境数据缺失」= 测试能执行但 staging 无对应数据。前者属本地可修复或需配置补齐，后者属数据补充轨道。

> **上下文提醒**：失败分类应反映问题根因（接口文档与实际实现不一致 / 服务端缺少校验 / 测试环境数据缺失等），不归咎于测试代码本身。只有在确认是 AI 对用例文档的解析/生成错误时，才归入「测试代码生成偏差」。

## 确认处理策略

向用户说明各分类的处理方式，获得用户明确确认后开始修复循环：

> 所有失败用例都需要修复至通过。按分类分轨处理：
> - **测试环境数据缺失** → 需要您提供真实测试数据
> - **接口文档与实际实现不一致** → 需要修复产物（yapi.md / qa-doc.md / 测试代码）
> - **服务端缺少参数校验 / 业务 bug** → AI 修复业务代码
> - **测试代码生成偏差** → AI 修正测试代码
> - **测试基础设施故障** → MUST 先按框架引用排查环境配置、中间件配置、HOST 回落值与连通性，确认非本地可修复后才可标记“需 staging”；禁止将未排查的配置问题直接归为环境不可达
>
> 确认开始？

用户确认后进入 Phase 4。
